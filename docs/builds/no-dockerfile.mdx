---
title: Build a repository without a Dockerfile
description: Turn on the agent builder so a model writes a Dockerfile that builds, then reuse it or commit it to the repository.
---

Set a Build's `builderRef` to `agent`, and Zeabur Builder builds a Git repository that has no Dockerfile. A model reads the code, writes a Dockerfile and trial-builds it. Then the run builds and pushes the image as usual. Later runs reuse that Dockerfile and do not call the model.

<Steps>

<Step>

### Create the Secret with the model API key

Get an API key from your model provider and save it as `./model-key`. This example uses Anthropic and the `team-a` Namespace, where the Build lives:

```sh
kubectl -n team-a create secret generic model --from-file=anthropic=./model-key
```

Every Namespace with a Build on the `agent` builder needs this Secret. Only the run's plan container gets the key.

</Step>

<Step>

### Turn on the agent builder

Upgrade the chart, keep your values and turn on `agent`:

```sh
helm upgrade builder oci://ghcr.io/zeabur-oss/charts/zeabur-builder --version <version> \
  -n builder-system --reuse-values \
  --set agent.enabled=true --set agent.provider=anthropic --set agent.model=claude-sonnet-5-5 \
  --set agent.auth.type=apiKey --set agent.auth.apiKey.name=model --set agent.auth.apiKey.key=anthropic
```

The chart installs a ClusterBuilder named `agent`. To send requests to another endpoint of the same API, such as a proxy, also set `agent.baseUrl`.

</Step>

<Step>

### Point a Build at the agent builder

Set `spec.builderRef` to `agent`:

```yaml
apiVersion: builder.zeabur.com/v1alpha1
kind: Build
metadata: {name: node-hello, namespace: team-a}
spec:
  source: {type: git, git: {url: https://github.com/heroku/nodejs-getting-started, ref: main}}
  builderRef: agent
```

</Step>

</Steps>

## Sign in without an API key

With Anthropic and OpenAI, a run can exchange a Kubernetes service account token for a short-lived access token, so no Namespace stores an API key. With Amazon Bedrock, a run assumes an IAM role with the token instead. First register the cluster with the provider as in "Use a service account token instead of an API key" in [Write a Dockerfile with AI](../reference/ai-dockerfile.mdx). Use the subject `system:serviceaccount:<namespace>:builder-agent`.

Create that ServiceAccount in each Namespace with a Build on the `agent` builder:

```sh
kubectl -n team-a create serviceaccount builder-agent
```

Set `agent.auth` in the chart values. For Anthropic:

```yaml
agent:
  enabled: true
  provider: anthropic
  model: claude-sonnet-5-5
  auth:
    type: anthropicFederation
    anthropicFederation:
      serviceAccountName: builder-agent
      federationRuleId: fdrl_…
      organizationId: …
```

Add `workspaceId` when the rule has several workspaces. `serviceAccountId` is optional. For OpenAI:

```yaml
agent:
  enabled: true
  provider: openai
  model: gpt-5.5
  auth:
    type: openaiFederation
    openaiFederation:
      serviceAccountName: builder-agent
      identityProviderId: …
      serviceAccountId: …
```

For Amazon Bedrock, the model is the Bedrock model ID:

```yaml
agent:
  enabled: true
  provider: aws_bedrock
  model: anthropic.claude-sonnet-5-5
  auth:
    type: awsFederation
    awsFederation:
      serviceAccountName: builder-agent
      roleArn: arn:aws:iam::<account>:role/<name>
      region: us-east-1
```

Only the plan container mounts the token, and only for the provider's audience. The run gets no token for the Kubernetes API. While the ServiceAccount is missing, the run waits with `ModelKeyMissing`.

## Read the result

List the Build's runs, then read `status.plan` of one of them:

```sh
kubectl -n team-a get buildrun -l builder.zeabur.com/build=node-hello
kubectl -n team-a get buildrun <run> -o jsonpath='{.status.plan}'
```

The first run of `node-hello` reported:

```json
{"dockerfile":"agent","inputTokens":10616,"language":"Node.js","modelCalled":true,"outputTokens":704,"port":5006,"runtimeVariables":["PORT"],"version":"24.9"}
```

| Field | Meaning |
| --- | --- |
| `dockerfile` | Where the Dockerfile came from: `repository` (the repository's own), `previous` (the last good one) or `agent` (the model wrote it). |
| `modelCalled`, `inputTokens`, `outputTokens` | Whether the model was called, and the tokens it used. |
| `language`, `version`, `port`, `buildVariables`, `runtimeVariables` | What the model found: the language and its version, the port, and the variables the build and the app read. |

The plan step's log has the whole Dockerfile, and its last line is the same report:

```sh
kubectl -n team-a logs job/<run> -c plan
```

What the model may read and its limits are in [Write a Dockerfile with AI](../reference/ai-dockerfile.mdx).

## Later runs

Each run that writes a new Dockerfile pushes its plan, the Dockerfile and what the agent reported, next to the Build's images, tagged `zeabur-plan-<Build uid>`. The Build records it in `status.plan`:

```sh
kubectl -n team-a get build node-hello -o jsonpath='{.status.plan}'
```

Later runs build that Dockerfile and do not call the model. Such a run reports `"dockerfile":"previous"` and `"modelCalled":false`, uses no tokens, and keeps the port, language and variables of the run that wrote it. Its status shows `"planSource":"saved"` and the plan's digest in `planDigest`.

If the saved Dockerfile no longer builds, for example after a dependency changed, the run fails. To have the model write a new one, annotate the Build with `fresh`:

```sh
kubectl -n team-a annotate build node-hello builder.zeabur.com/plan=fresh
```

While the annotation is set, every run calls the model. After a run has built, remove it, and later runs reuse the new Dockerfile:

```sh
kubectl -n team-a annotate build node-hello builder.zeabur.com/plan-
```

## Commit the Dockerfile to the repository

To take the Dockerfile out of the model's hands, fetch the saved plan with [oras](https://oras.land):

```sh
plan=$(kubectl -n team-a get build node-hello -o jsonpath='{.status.plan.image}')
layer=$(oras manifest fetch "$plan" | jq -r '.layers[0].digest')
mkdir plan && oras blob fetch --output - "${plan%@*}@$layer" | tar -xz -C plan
```

Commit both `plan/Dockerfile` and `plan/Dockerfile.dockerignore` to the repository. The second file keeps out the files the agent excluded, credentials among them; without it, a `COPY . .` copies them into the image. Then set the Build's `builderRef` to `dockerfile`. You can now change the files like any others.

## Troubleshooting

| What you see | What to do |
| --- | --- |
| The run waits with `ModelKeyMissing`, and its message names a missing Secret, key or ServiceAccount. | Create it, or add the key, in the Build's Namespace. The run starts by itself; no Job is created while it waits. |
| The run fails with `PlanFailed`. | Read `status.plan.stopped` for the reason and `status.message` for what to do. |
| `stopped` is `ModelKeyMissing` or `ModelFailed`. | Check the key or the federation, and `status.message`. A missing or refused key or service account token is `ModelKeyMissing`; a refused or failed request to the model API is `ModelFailed`. |
| `stopped` is `SeveralApps`. | Set the app's folder in `spec.source.contextDir`. |
| `stopped` is `NeedsBuildVariable`. | Set the variable that `status.message` names in `spec.env`. The agent's trial builds get it as a secret, so the next run can finish the Dockerfile. |
| `stopped` is `NoAppFound`, `NeedsPrivateDependency` or `UnsupportedPlatform`. | `status.message` says what the app, its private dependency or its platform needs. |
| `stopped` is `BudgetSpent` or `BuildKeepsFailing`. | Read `status.message`. `BudgetSpent` means a limit was reached: model calls, failed builds, time or tokens. |
