Zeabur Builder has no releases yet. The API is `v1alpha1`.

## Features verified on a cluster

The following scripts have verified the current `main` branch on a k3s 1.36 cluster. CI also runs these scripts through [`scripts/ci/kubernetes.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/ci/kubernetes.sh).

- [`scripts/deploy-example.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/deploy-example.sh)
- [`scripts/example-isolation.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/example-isolation.sh)
- [`scripts/example-admission.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/example-admission.sh)
- [`scripts/example-archive.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/example-archive.sh)

Verification covers the following behavior:

| Feature | Verified behavior |
| --- | --- |
| Public repository builds | Polling can trigger Dockerfile and Railpack builds. |
| Source errors | `SourceReady` and BuildRun report failure when the ref or Dockerfile can't be found. |
| buildkitd lifecycle | Each Namespace has one buildkitd that starts on demand and scales down to 0 when idle. |
| Namespace isolation | The system rejects client certificates from other Namespaces, access to registry paths and Pods from other Namespaces, and pushes without a token. |
| Network access during builds | `RUN` can access the internet and the registry, but can't access Services, the Kubernetes API, or 169.254.169.254. |
| Archive sources | Builds can use archives by digest. A Build in another Namespace or with a different name fails at the source stage when it uses the same digest. |
| ValidatingAdmissionPolicy | The controller's ServiceAccount can create build Jobs and buildkitd. The policy rejects privileged Jobs, Jobs in `kube-system`, and Jobs that use other images, host paths, host networking, or other ServiceAccounts. It also rejects other StatefulSets. `scripts/example-admission.sh` verifies this behavior. |

## Known issues

The controller's ClusterRole currently has `get`, `create`, `update`, and `delete` permissions for Secrets in all Namespaces. The controller uses these permissions to read Secrets specified by Builds and write copies.

The controller only needs access to Secrets with the `builder.zeabur.com/git-credentials` or `builder.zeabur.com/push-credentials` label and copies that the controller creates. The current ClusterRole grants permissions beyond this requirement.
