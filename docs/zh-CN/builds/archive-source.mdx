将文件夹打包并推送到镜像仓库（registry），再把 OCI artifact 的 manifest digest 写入 `Build`，就能从上传的文件夹构建镜像，无需使用 Git ref。

## 开始前

- 准备要构建的文件夹。持有文件夹的客户端，例如 Zeabur 或 `zeaburctl`，负责上传。
- 准备 `Build` 的上传令牌（token）。客户端在 `Build` 上添加 `builder.zeabur.com/upload-token-request` annotation 来请求令牌，再用这个令牌推送。获取方式见 [Registry 令牌](../operations/registry-tokens.mdx)。
- 要使用下方命令，你需要准备 [ORAS](https://oras.land)，以及 `Build` 上传用 Secret 中的 `auth.json`。

## 上传并配置 Build

<Steps>

<Step>

### 确认 artifact 的仓库位置

`Build` 决定 artifact 的仓库位置，格式固定为：

```text
<registry.host>/<namespace>/<build name>/source
```

`Build` 只需指定 digest。Job 会从自身所属 Namespace 中、对应这个 `Build` 的仓库下载归档文件。

如果 registry 在该仓库中找不到 manifest，本次构建会失败，原因为 `SourceFailed`。

</Step>

<Step>

### 打包文件夹并推送 artifact

客户端必须先推送 artifact，再将 digest 写入 `Build`。新的 `Build` 可以先不设置 `digest`，等上传完成后再填入。

artifact 使用 [OCI image manifest](https://github.com/opencontainers/image-spec/blob/v1.1.1/manifest.md)，格式与 `oras push` 写入的格式相同：

| 字段 | 值 |
|---|---|
| `mediaType` | `application/vnd.oci.image.manifest.v1+json` |
| `artifactType` | `application/vnd.zeabur.source.v1+tar` |
| `config` | 空 descriptor：`application/vnd.oci.empty.v1+json`，内容为 `{}` |
| `layers` | 恰好一个，类型为 `application/vnd.oci.image.layer.v1.tar+gzip`，内容是用 gzip 压缩的文件夹 tar 归档文件 |

在要上传的文件夹中执行以下命令，使用 `Build` 上传用 Secret 中的 `auth.json`：

```sh
tar -czf /tmp/source.tar.gz .
cd /tmp && oras push --registry-config auth.json \
  zot.zot.svc:5000/team-a/api/source:upload-$(date +%s) \
  --artifact-type application/vnd.zeabur.source.v1+tar \
  source.tar.gz:application/vnd.oci.image.layer.v1.tar+gzip
```

`oras push` 会输出 digest。[`scripts/example-archive.sh`](https://github.com/zeabur-oss/builder/blob/main/scripts/example-archive.sh) 使用 `curl` 完成相同操作。

<Callout type="warn">

推送 manifest 时要添加标签（tag），不要只用 digest 推送。[Zeabur Catalog](https://github.com/zeabur-oss/catalog) 使用的 Zot 等 registry 会删除没有标签的 manifest，在构建开始前就会清理这类上传内容。

</Callout>

</Step>

<Step>

### 将 manifest digest 写入 Build

将上传后获取的 manifest digest 填入 `spec.source.archive.digest`：

```yaml
apiVersion: builder.zeabur.com/v1alpha1
kind: Build
metadata: {name: api, namespace: team-a}
spec:
  source:
    archive: {digest: "sha256:<manifest digest>"}
  builderRef: railpack
```

`source` 必须在 `git` 和 `archive` 中选择一个配置。归档文件来源和 Git 来源一样支持 `contextDir` 与 `dockerfile`，但不支持 `credentialsRef`、`githubApp` 或 webhook 触发。

要构建新上传的内容，更新 `digest`。

</Step>

</Steps>

## 大小限制与解压规则

- layer 压缩后最大为 256 MiB，解压后的 tar 流最大为 1 GiB。达到上限时，Job 会停止解压。
- 如果归档条目的路径为绝对路径或包含 `..`，Job 会停止解压。
- 符号链接必须使用相对目标路径，且不能向上超出文件夹根目录。
- 硬链接必须指向归档文件中更早出现的普通文件。
- 解压时会跳过设备文件与 FIFO。
- 如果归档文件中的文件带有执行权限位，解压后的权限为 0755；否则为 0644。解压时不会保留所有者与时间信息。

## 确认结果

`BuildRun` 的 `revision`，以及 `Build` 的 `status.remoteRevision` 和 `status.latestRevision`，都会记录 manifest digest。`status.resolvedRef` 保持为空。

镜像标签以 `archive` 作为分支名称，并使用 digest 开头的七个十六进制数字，例如：

```text
archive-1761058800-3e1a9c2
```

构建不会发送 commit status。

## 旧归档文件的保留方式

registry 清理这些内容或你删除所属的 `Build` 之前，每次上传的内容都会留在 registry。删除 `Build` 时的清理方式见 [Registry 令牌](../operations/registry-tokens.mdx)。

Zeabur Catalog 中的 Zot 会保留每个仓库最近推送的 20 个标签，并在两小时后删除没有标签的 manifest。因此，`<namespace>/<build>/source` 会保留最近的 20 次上传。

如果使用其他 registry，请为 `*/*/source` 设置保留策略。
