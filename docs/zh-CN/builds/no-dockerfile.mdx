---
title: 构建没有 Dockerfile 的仓库
description: 启用 agent 构建器，让模型写出能构建的 Dockerfile，之后的构建会沿用，也可以提交进仓库。
---

把 Build 的 `builderRef` 设为 `agent`，Zeabur Builder 就能构建没有 Dockerfile 的 Git 仓库：模型读取代码、写出 Dockerfile 并试着构建，然后照常构建并推送镜像。之后的构建会沿用这份 Dockerfile，不必再调用模型。

<Steps>

<Step>

### 创建存放模型 API 密钥的 Secret

从模型提供商获取 API 密钥，保存为 `./model-key`。下面以 Anthropic 为例，在 Build 所在的 `team-a` Namespace 创建 Secret：

```sh
kubectl -n team-a create secret generic model --from-file=anthropic=./model-key
```

每个有 Build 使用 `agent` 构建器的 Namespace 都需要这个 Secret。只有构建时的 plan 容器能拿到密钥。

</Step>

<Step>

### 启用 agent 构建器

升级 chart，保留原有配置并启用 `agent`：

```sh
helm upgrade builder oci://ghcr.io/zeabur-oss/charts/zeabur-builder --version <version> \
  -n builder-system --reuse-values \
  --set agent.enabled=true --set agent.provider=anthropic --set agent.model=claude-sonnet-5-5 \
  --set agent.auth.type=apiKey --set agent.auth.apiKey.name=model --set agent.auth.apiKey.key=anthropic
```

chart 会安装名为 `agent` 的 ClusterBuilder。要改用同一个 API 的其他端点，例如代理服务器，再设置 `agent.baseUrl`。

</Step>

<Step>

### 让 Build 使用 agent 构建器

把 `spec.builderRef` 设为 `agent`：

```yaml
apiVersion: builder.zeabur.com/v1alpha1
kind: Build
metadata: {name: node-hello, namespace: team-a}
spec:
  source: {type: git, git: {url: https://github.com/heroku/nodejs-getting-started, ref: main}}
  builderRef: agent
```

</Step>

</Steps>

## 不用 API 密钥登录

使用 Anthropic 和 OpenAI 时，run 可以用 Kubernetes 服务账号令牌换取短期访问令牌，Namespace 里就不用存放 API 密钥。使用 Amazon Bedrock 时，run 改用令牌代入 IAM 角色。先按照 [用 AI 写 Dockerfile](../reference/ai-dockerfile.mdx) 中“用服务账号令牌代替 API 密钥”一节，在提供商处登记集群。subject 填 `system:serviceaccount:<namespace>:builder-agent`。

在每个有 Build 使用 `agent` 构建器的 Namespace 创建这个 ServiceAccount：

```sh
kubectl -n team-a create serviceaccount builder-agent
```

在 chart 配置值中设置 `agent.auth`。Anthropic 的写法：

```yaml
agent:
  enabled: true
  provider: anthropic
  model: claude-sonnet-5-5
  auth:
    type: anthropicFederation
    anthropicFederation:
      serviceAccountName: builder-agent
      federationRuleId: fdrl_…
      organizationId: …
```

规则涵盖多个工作区时，再加上 `workspaceId`。`serviceAccountId` 可以不填。OpenAI 的写法：

```yaml
agent:
  enabled: true
  provider: openai
  model: gpt-5.5
  auth:
    type: openaiFederation
    openaiFederation:
      serviceAccountName: builder-agent
      identityProviderId: …
      serviceAccountId: …
```

使用 Amazon Bedrock 时，model 填 Bedrock 的模型 ID：

```yaml
agent:
  enabled: true
  provider: aws_bedrock
  model: anthropic.claude-sonnet-5-5
  auth:
    type: awsFederation
    awsFederation:
      serviceAccountName: builder-agent
      roleArn: arn:aws:iam::<account>:role/<name>
      region: us-east-1
```

只有 plan 容器会挂载令牌，而且令牌只用于提供商的 audience。run 拿不到 Kubernetes API 的令牌。ServiceAccount 不存在时，run 会停在 `ModelKeyMissing` 等待。

## 查看结果

列出这个 Build 的 BuildRun，再查看其中一个的 `status.plan`：

```sh
kubectl -n team-a get buildrun -l builder.zeabur.com/build=node-hello
kubectl -n team-a get buildrun <run> -o jsonpath='{.status.plan}'
```

`node-hello` 第一次构建的结果如下：

```json
{"dockerfile":"agent","inputTokens":10616,"language":"Node.js","modelCalled":true,"outputTokens":704,"port":5006,"runtimeVariables":["PORT"],"version":"24.9"}
```

| 字段 | 含义 |
| --- | --- |
| `dockerfile` | Dockerfile 从哪里来：`repository` 是仓库自己的，`previous` 是上次成功的那份，`agent` 是模型写的。 |
| `modelCalled`、`inputTokens`、`outputTokens` | 有没有调用模型，以及用了多少 token。 |
| `language`、`version`、`port`、`buildVariables`、`runtimeVariables` | 模型找到的语言和版本、端口，以及构建和应用会读取的变量。 |

plan 步骤会在日志打印完整的 Dockerfile，最后一行就是上面的结果：

```sh
kubectl -n team-a logs job/<run> -c plan
```

模型能读取哪些内容、有哪些限制，请见[用 AI 写 Dockerfile](../reference/ai-dockerfile.mdx)。

## 之后的构建

每次写出新的 Dockerfile 并构建成功后，都会把这次的 plan（Dockerfile 和 agent 报告的内容）推送到 Build 的镜像旁边，标签是 `zeabur-plan-<Build uid>`，Build 也会记在 `status.plan`：

```sh
kubectl -n team-a get build node-hello -o jsonpath='{.status.plan}'
```

之后的构建会直接用这份 Dockerfile，不再调用模型。这种构建的结果是 `"dockerfile":"previous"`、`"modelCalled":false`，不用任何 token，端口、语言和变量也和写出这份 Dockerfile 的那次一样。BuildRun 的 status 会显示 `"planSource":"saved"`，`planDigest` 是这份 plan 的 digest。

如果保存的 Dockerfile 已经构建不了，例如依赖改了，这次构建会失败。要让模型重写一份，给 Build 加上 `fresh` annotation：

```sh
kubectl -n team-a annotate build node-hello builder.zeabur.com/plan=fresh
```

有这个 annotation 时，每次构建都会调用模型。构建成功后把它去掉，之后的构建就会沿用新的 Dockerfile：

```sh
kubectl -n team-a annotate build node-hello builder.zeabur.com/plan-
```

## 把 Dockerfile 提交进仓库

不想再让模型决定 Dockerfile 的话，用 [oras](https://oras.land) 取回保存的 plan：

```sh
plan=$(kubectl -n team-a get build node-hello -o jsonpath='{.status.plan.image}')
layer=$(oras manifest fetch "$plan" | jq -r '.layers[0].digest')
mkdir plan && oras blob fetch --output - "${plan%@*}@$layer" | tar -xz -C plan
```

把 `plan/Dockerfile` 和 `plan/Dockerfile.dockerignore` 两个文件都提交进仓库。第二个文件会排除 agent 有意略过的文件，包括凭据；少了它，`COPY . .` 会把这些文件复制进镜像。再把 Build 的 `builderRef` 改成 `dockerfile`，之后就像普通文件一样自己修改。

## 遇到问题

| 看到的情况 | 接下来怎么做 |
| --- | --- |
| run 停在 `ModelKeyMissing` 等待，消息说找不到 Secret、键或 ServiceAccount | 在 Build 所在的 Namespace 创建它，或补上键。补好后 run 会自己开始，等待时不会创建 Job。 |
| run 以 `PlanFailed` 失败 | 从 `status.plan.stopped` 看停止原因，从 `status.message` 看怎么处理。 |
| `stopped` 是 `ModelKeyMissing` 或 `ModelFailed` | 检查密钥或工作负载身份联合配置，以及 `status.message`。密钥或服务账号令牌缺失或被拒绝是 `ModelKeyMissing`；模型 API 拒绝请求或请求失败是 `ModelFailed`。 |
| `stopped` 是 `SeveralApps` | 在 `spec.source.contextDir` 指定应用所在的目录。 |
| `stopped` 是 `NeedsBuildVariable` | 在 `spec.env` 里设置 `status.message` 指出的变量。agent 的试构建会以 secret 拿到这个变量，下一次运行就能写完 Dockerfile。 |
| `stopped` 是 `NoAppFound`、`NeedsPrivateDependency` 或 `UnsupportedPlatform` | `status.message` 会说明应用、私有依赖或平台需要什么。 |
| `stopped` 是 `BudgetSpent` 或 `BuildKeepsFailing` | 查看 `status.message`。`BudgetSpent` 表示到了上限：模型调用次数、构建失败次数、时间或 token。 |
