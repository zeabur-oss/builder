建立 `Build`，指定 Git 儲存庫與建置器。控制器會為新的 commit 建置映像檔，推送到 registry，再將映像檔資訊寫入 `BuildRun` 與 `Build`。

## 建置流程

<Steps>

<Step>

### 解析 Git commit

控制器會使用 Git 的 smart HTTP 或 SSH 協定，找出 `Build` 的 ref 對應的 commit。

省略 `ref` 時，控制器會追蹤儲存庫的預設分支，並將分支名稱寫入 `status.resolvedRef`。

</Step>

<Step>

### 建立 BuildRun 與 Job

控制器找到新的 commit 後，會建立 `BuildRun`，再為這次建置建立 Job。

</Step>

<Step>

### 執行建置

Job 會擷取該 commit。如果建置器提供規劃器，Job 會先執行規劃器，再執行 `buildctl`，連線到所屬 Namespace 的 buildkitd。

控制器會在需要時啟動 buildkitd。Dockerfile 的 `RUN` 步驟會在 buildkitd 中執行，與 Pod、Service 和節點隔離。

</Step>

<Step>

### 推送映像檔並記錄結果

建置完成後，映像檔會推送到 `<registry.host>/<namespace>/<name>`，digest 與 tag 會寫入 `BuildRun` 和 `Build`。

`Build` 的 `status.latestImage` 會用 `<repository>:<tag>@<digest>` 格式記錄映像檔。

</Step>

</Steps>

## 每個 Namespace 的建置資源

每個執行建置的 Namespace 都有自己的 buildkitd、快取、憑證授權單位（CA）與 registry 路徑。

buildkitd 的磁碟區會保留快取，供後續建置使用，因此 `RUN --mount=type=cache` 的內容可以保留。這些快取不會推送到 registry。

buildkitd 閒置 10 分鐘後會縮到零。

改了快取大小或儲存類別後，該 Namespace 下次開始建置時，控制器會換掉它的 buildkitd 和快取，換之前會先等進行中的建置跑完。如果 Kubernetes 拒絕新的 buildkitd，舊的會保留，這次建置以 `InfraError` 失敗，並附上 Kubernetes 的訊息。

## 建置權限與隔離

每次建置都有一個 Job。Job 會執行 `buildctl`，不需要特權。

## 自訂資源

Zeabur Builder 使用 `Build`、`BuildRun` 與 `ClusterBuilder` 三種自訂資源，API 版本為 `v1alpha1`。

`Build` 用來指定 Git 儲存庫與建置器。控制器會為新的 commit 建立 `BuildRun`，記錄這次建置的狀態與結果。

## 確認結果

檢視各個 Build 的建置器、來源、版本與就緒狀態：

```sh
kubectl get builds
```

加上 `-o wide` 就能檢視映像檔。

檢視每次建置的階段、原因、開始與結束時間：

```sh
kubectl get buildruns
```

建置日誌就是 Job 的 Pod 日誌。建置步驟每行輸出一個 JSON 事件，用 `jq -r '.text // .message // .name'` 可以讀成文字。
